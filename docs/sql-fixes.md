# Расхождения между ТЗ и выполняемым SQL

Логика выявления бенефициарных собственников перенесена из ТЗ без изменений.
Ниже перечислено всё, что пришлось поправить, чтобы запросы вообще запускались,
и всё, что осталось под вопросом и требует подтверждения заказчика.

---

## 1. Синтаксические правки (логика не менялась)

### БС-4 — обращение к CTE по имени вместо псевдонима

Файл: `backend/app/algorithms/sql/bs_04.sql`

| | |
|---|---|
| В ТЗ | `left join table1 b on a.taxpayer_iin_bin = table1.taxpayer_iin_bin` |
| Выполняется | `left join table1 b on a.taxpayer_iin_bin = b.taxpayer_iin_bin` |

CTE подключён под псевдонимом `b`; после присвоения псевдонима ClickHouse
не разрешает обращаться к CTE по исходному имени. Смысл соединения не изменился.

Там же в `status` квалифицированы ссылки на `founder_iin_bin` → `b.founder_iin_bin`
(в ТЗ они были неквалифицированными).

### БС-17 — имя колонки в соединении с результатом БС-22

Файл: `backend/app/algorithms/sql/bs_17.sql`

| | |
|---|---|
| В ТЗ | ``LEFT JOIN AFM_6_TEST.AFM_6_1_28 bs22 ON a1.taxpayer_iin_bin2 = bs22.`k.taxpayer_iin_bin` `` |
| Выполняется | `LEFT JOIN AFM_6_TEST.AFM_6_1_28 bs22 ON a1.taxpayer_iin_bin2 = bs22.taxpayer_iin_bin` |

В SQL алгоритма БС-22 колонка объявлена как `k.taxpayer_iin_bin AS taxpayer_iin_bin`,
то есть её итоговое имя — `taxpayer_iin_bin`.

### Ключ сортировки таблиц результатов

Для всех таблиц результатов используется
`ENGINE = MergeTree ORDER BY (assumeNotNull(taxpayer_iin_bin))`.

В ТЗ для БС-1, БС-3 и БС-4 указано `order by taxpayer_iin_bin`, а для БС-13 —
`ORDER BY (assumeNotNull(taxpayer_iin_bin))`. Форма с `assumeNotNull` выбрана
единой: она работает и с Nullable-колонками, а на не-Nullable не влияет.

## 3. Промежуточные таблицы БС-13

ТЗ описывает шаги 1–5 текстом и приводит SQL только для финального шага 6.
SQL шагов 1–5 написан строго по описанию:

| Шаг | Таблица | Что делает |
|---|---|---|
| 1 | `tmp_esf_customer` | покупатели с оборотом > 50 млн ₸ за 365 дней; оба участника ЮЛ (пятый знак справа `4`/`5`), длина ИИН/БИН = 12, нет кавычек в значении |
| 2 | `tmp_esf_pairs` | пары покупатель-поставщик, где `pair_turnover * 2 >= total_turnover` (доля поставщика ≥ 50 %) |
| 3 | `tmp_bs_buyer` | БС-1, БС-3 и ФЛ-учредители покупателей из шага 2 |
| 4 | `tmp_seller_founders` | учредители и директора поставщиков из шага 2 |
| 5 | `tmp_links` | родственные связи (`vid_sviazi = 'rod_sviaz'`) в обе стороны, только для ИИН из шага 3 |

**Требует подтверждения:** имена колонок таблицы `pfr_dashboard.svz_overroll_table`.
В ТЗ они не описаны; в шаге 5 использованы `iin_1` и `iin_2` — по именам, которыми
финальный запрос ТЗ обращается к `tmp_links`.

## 4. Открытые вопросы к заказчику

### 4.1. БС-8: КВО 0911 или 921

Текст ТЗ: «КВО **0911** — переводы ЮЛ к ФЛ только если…».
SQL ТЗ: `OPER_IDVIEW = '921'`.

Выполняется значение из SQL — **`'921'`**, поскольку SQL является исполняемой
частью требования. Остальные КВО в текстовой и SQL-частях совпадают
(0511/0530/0311 → `'511'`, `'530'`, `'311'`).

**Нужно решение:** какое значение верное. Правится в `bs_algorithms.sql_script`
без пересборки.

### 4.2. Поле `category` в итоговой таблице

Текст ТЗ: «Для получения категории компании выполняется LEFT JOIN с
**AFM_2_1.AFM_2_1_8** по taxpayer_iin_bin, берётся поле `category`».

Словарь таблиц в том же ТЗ описывает `AFM_2_1_8` как содержащую
`taxpayer_iin_bin`, `ownership_type`, `_actual_date`, а поле `category`
(организационно-правовая форма) — у `AFM_2_1_TEST.AFM_2_1_9`.

Реализация: при старте приложение проверяет по `system.columns`, есть ли
`category` в `AFM_2_1_8`. Если есть — берёт оттуда, как указано в тексте ТЗ;
если нет — из `AFM_2_1_9`. Фактический выбор пишется в журнал при запуске.
См. `registry_service.detect_category_source()`.

### 4.3. Доля участия из `AFM_6_1_5_1`

Текст ТЗ: «Для получения доли участия выполняется LEFT JOIN с
`AFM_6_TEST.AFM_6_1_5_1` **по benefeciary_iin_bin**».

Соединение выполнено именно так, как написано. Обратите внимание: таблица
содержит пары компания-бенефициар, и соединение только по бенефициару даёт долю
безотносительно компании. Чтобы избежать размножения строк, значение сворачивается
до одного на бенефициара (`any(share_percentage)`).

**Нужно решение:** не следует ли соединять по паре
`taxpayer_iin_bin + benefeciary_iin_bin`.

### 4.4. Суммирование баллов ball1 и ball2

Текст ТЗ: «ball1 — общая сумма баллов priority **по всем строкам** с данным
taxpayer_iin_bin; ball2 — сумма баллов priority **по строкам** с данной парой».

Таблицы алгоритмов содержат несколько строк на одну пару компания-бенефициар —
это следствие соединений с учредителями и директорами. При буквальном суммировании
«по строкам» ball1 и ball2 зависели бы от числа учредителей компании, а не от
набора сработавших алгоритмов, и ball3 потерял бы смысл (например, у компании
с пятью учредителями все баллы выросли бы в пять раз).

Реализация: балл учитывается один раз на сочетание «пара + алгоритм»
(`priority` внутри одного алгоритма — константа). Формула ball3 из ТЗ сохранена:
`round(ball2 / ball1 * 100, 2)`.

См. `backend/app/algorithms/registry_sql.py`.

### 4.5. Колонка `taxpayer_name` в `AFM_2_1_5_1`

SQL алгоритма БС-3 (из ТЗ) обращается к `taxpayer_name` в таблице
`AFM_2_1_TEST.AFM_2_1_5_1`, тогда как словарь таблиц ТЗ такой колонки у неё
не описывает. SQL оставлен без изменений. Если колонки в контуре действительно
нет, БС-3 упадёт с ошибкой — она будет видна в интерфейсе управления
алгоритмами и в `logs/algorithms.log`.

### 4.6. Алгоритмы, упомянутые, но не описанные

* **БС-5** — упоминается в текстовом описании БС-17 как последний шаг цепочки
  установления конечного ФЛ-бенефициара. В SQL БС-17 из ТЗ цепочка
  заканчивается на БС-4, поэтому запрос самодостаточен и работает без БС-5.
* **БС-19** — присутствует только в расшифровке алгоритмов для промптов Qwen
  («данные от Министерства энергетики о недропользователях»); расчётный
  алгоритм и SQL в ТЗ не приведены. Расшифровка в справочнике оставлена,
  алгоритм не реализован.
* **БС-12, БС-14, БС-15, БС-18, БС-20, БС-21** — в ТЗ отсутствуют.
* Таблица `AFM_2_13.AFM_2_13_1` (МИИР, недропользователи) описана в словаре
  таблиц, но ни один приведённый алгоритм её не использует.

Добавить недостающие алгоритмы можно через интерфейс управления алгоритмами
(кнопка «Добавить алгоритм») — без изменения кода.
