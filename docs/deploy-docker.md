# Развёртывание через Docker

Сервер `10.10.31.35` — Linux amd64, интернета нет. Образы собираются
на машине с интернетом и переносятся архивом.

Результат: интерфейс и API на **http://10.10.31.35:8020**.

---

## Схема

```
   машина с интернетом                       сервер 10.10.31.35
   ────────────────────                      ──────────────────
   docker build                              docker load  -i images.tar
   docker pull postgres                      docker compose up -d
   docker save  →  images.tar    ── tar ──▶
                                             ┌──────────────────────────┐
                                             │ reestr-bs-app  :8020     │
                                             │ reestr-bs-postgres       │
                                             └──────────────────────────┘
                                                 │            │
                                        ClickHouse       Qwen / Ollama
                                     192.168.122.45     192.168.97.8
```

PostgreSQL поднимается контейнером — ставить его на сервер отдельно не нужно.
ClickHouse и Qwen остаются внешними: контейнер обращается к ним по сети.

---

## Часть 1. Сборка комплекта (машина с интернетом)

Нужен Docker. Node.js и Python на этой машине не требуются — всё собирается
внутри образа.

```bash
./scripts/build-release.sh 1.0.0
```

На Windows:

```powershell
.\scripts\build-release.ps1 -Version 1.0.0
```

Скрипт собирает образ приложения, скачивает `postgres:16-alpine`, выгружает оба
в `images.tar` и упаковывает всё в `reestr-bs-1.0.0.tar`.

Внутри архива четыре файла, **без вложенного каталога** — распаковываются
прямо в текущую папку:

| Файл | Назначение |
|---|---|
| `images.tar` | образы приложения и PostgreSQL |
| `docker-compose.yml` | описание запуска |
| `.env.example` | шаблон конфигурации |
| `INSTALL.md` | этот документ |

Размер — около 188 МБ. Архив не сжимается: слои образов уже сжаты, gzip
экономил бы порядка 2 МБ, зато добавлял лишний шаг при распаковке.

В конце сборки печатается контрольная сумма SHA256 — по ней сверяется
целостность после переноса.

### Что делает сборка образа

Двухэтапный `Dockerfile`:

1. `node:20-alpine` — `npm ci` по `package-lock.json`, затем `npm run build`.
   Интерфейс собирается воспроизводимо, версии зависимостей зафиксированы.
2. `python:3.11-slim` — установка зависимостей из `requirements.txt`, копирование
   кода и готового `dist` из первого этапа.

Версия Python зафиксирована образом — подбирать её под сервер не нужно,
как и переносить `backend/wheels`.

Приложение работает от пользователя `reestr` (uid 10001), не от root.

## Часть 2. Установка на сервер

### 1. Перенести и распаковать

С машины, имеющей доступ к серверу:

```bash
scp reestr-bs-1.0.0.tar root@10.10.31.35:~/
```

На сервере:

```bash
sha256sum ~/reestr-bs-1.0.0.tar        # сверить с суммой из вывода сборки

mkdir -p ~/reestr-bs && cd ~/reestr-bs
tar xf ~/reestr-bs-1.0.0.tar
ls -la
```

Файлы ложатся прямо в `~/reestr-bs`, подкаталогов не создаётся.

### 2. Загрузить образы

```bash
docker load -i images.tar
docker images | grep -E "reestr-bs|postgres"
```

Должны появиться `reestr-bs:1.0.0` и `postgres:16-alpine`.

### 3. Заполнить конфигурацию

```bash
cp .env.example .env
nano .env
```

Обязательно заполнить три пустых значения:

| Параметр | Как получить |
|---|---|
| `POSTGRES_PASSWORD` | придумать пароль для БД метаданных |
| `SECRET_KEY` | `openssl rand -base64 64 \| tr -d '\n'` |
| `FIRST_SUPERUSER_PASSWORD` | пароль администратора системы |

Проверить и при необходимости поправить: `CLICKHOUSE_USER`,
`CLICKHOUSE_PASSWORD`, `OLLAMA_MODEL`.

Имя модели должно совпадать с зарегистрированным в Ollama буква в букву:

```bash
curl http://192.168.97.8:11434/api/tags
```

Если compose ругается `задайте POSTGRES_PASSWORD в файле .env` — значение
осталось пустым.

### 4. Запустить

```bash
docker compose up -d
docker compose ps
```

Приложение стартует после того, как PostgreSQL пройдёт проверку готовности —
за это отвечает `depends_on: condition: service_healthy`.

### 5. Проверить

```bash
docker compose logs -f app
```

В журнале при старте должно быть:

```
Интерфейс раздаётся из /app/frontend/dist
ИИ Qwen:    http://192.168.97.8:11434 (qwen3.5-122b)
Схема PostgreSQL проверена/создана
Создан администратор по умолчанию: admin
В bs_algorithms добавлено алгоритмов: 14
ClickHouse доступен, версия ...
Поле category берётся из ...
```

Затем:

| Адрес | Что должно быть |
|---|---|
| `http://10.10.31.35:8020` | страница входа |
| `http://10.10.31.35:8020/api/docs` | документация API (работает без интернета) |
| `http://10.10.31.35:8020/api/health` | `status: ok`, все три системы доступны |

Открыть порт, если включён firewall:

```bash
sudo firewall-cmd --add-port=8020/tcp --permanent && sudo firewall-cmd --reload
# либо
sudo ufw allow 8020/tcp
```

### 6. Первый расчёт

Войти администратором → раздел **Алгоритмы**.

Запускать по одному, начиная с независимых: БС-1, БС-2, БС-3, БС-4, БС-22 —
так сразу видно, какой алгоритм упал и на чём. Затем зависимые: БС-11, БС-13,
БС-17. Потом остальные. После проверки — «Пересчитать всё».

БС-13 читает ЭСФ (~485 млн строк) и выполняется часами.

## Эксплуатация

```bash
docker compose ps                    # состояние контейнеров
docker compose logs -f app           # журнал приложения
docker compose restart app           # перезапуск
docker compose down                  # остановить (данные сохраняются)
docker compose up -d                 # запустить снова
```

Файловые журналы лежат в томе `reestr-bs-logs`:

```bash
docker compose exec app ls -la /app/logs
docker compose exec app tail -n 200 /app/logs/algorithms.log
```

### Данные

| Том | Что хранит | При `docker compose down` |
|---|---|---|
| `reestr-bs-postgres-data` | SQL алгоритмов, история правок, пользователи | сохраняется |
| `reestr-bs-data` | настройки, заданные через интерфейс (с паролями) | сохраняется |
| `reestr-bs-logs` | журналы | сохраняется |

Результаты алгоритмов лежат в ClickHouse и от контейнеров не зависят вообще.

**`docker compose down -v` удаляет тома вместе с данными** — SQL алгоритмов
и учётные записи будут потеряны. Без флага `-v` данные остаются.

Резервная копия метаданных:

```bash
docker compose exec postgres pg_dump -U bs_registry bs_registry > bs_registry_$(date +%F).sql
```

## Обновление версии

1. На машине с интернетом: `./scripts/build-release.sh 1.1.0`
2. Перенести архив, распаковать, `docker load -i images.tar`
3. В `.env` изменить `VERSION=1.1.0`
4. `docker compose up -d` — compose пересоздаст только контейнер приложения

Откат: вернуть прежнее значение `VERSION` и повторить `docker compose up -d`.
Старый образ остаётся в системе, пока его не удалили `docker image prune`.

## Если что-то не работает

**Контейнер приложения перезапускается.** Смотреть `docker compose logs app`.
Частая причина — пустой `SECRET_KEY` или неверный `POSTGRES_PASSWORD`.

**`status: degraded` в `/api/health`.** Приложение работает, но не видит
ClickHouse или Qwen. Проверить доступность с самого сервера:

```bash
curl http://192.168.122.45:8123/ping
curl http://192.168.97.8:11434/api/tags
```

Если с сервера они отвечают, а из контейнера нет — вопрос в сетевых политиках
для docker-моста; проверить изнутри:

```bash
docker compose exec app python -c "import urllib.request;print(urllib.request.urlopen('http://192.168.122.45:8123/ping',timeout=5).read())"
```

**Интерфейс открывается, данных нет.** Алгоритмы ещё не считались — таблиц
результатов в ClickHouse нет. Раздел «Алгоритмы» → «Пересчитать всё».

**Поменяли адрес в `.env`, перезапустили — система ходит по-старому.**
Почти наверняка адрес был ранее сохранён через раздел «Настройки», а сохранённые
настройки сильнее переменных окружения. Проверить и поправить можно в самом
разделе: у блока показано, откуда взято значение — «изменено через интерфейс»
или «из окружения». Полный сброс к переменным окружения:

```bash
docker compose exec app python -c "import pathlib; pathlib.Path('/app/data/settings.json').unlink(missing_ok=True)"
docker compose restart app
```

**Порт 8020 занят.** Изменить левую часть в `docker-compose.yml`:
`"8021:8020"` — внешний порт станет 8021, внутренний остаётся прежним.
