# Реестр БС — установка на сервер 10.10.31.35

Система выявления бенефициарных собственников. Агентство по финансовому
мониторингу Республики Казахстан.

Сервер изолирован: интернета нет. Всё необходимое лежит в этом комплекте.

---

## Что внутри

| Файл | Назначение |
|---|---|
| `images.tar.gz` | образы `reestr-bs:1.0` и `postgres:16` |
| `docker-compose.yml` | конфигурация запуска, **под `docker-compose` 1.x** |
| `docker-compose.v2.yml` | вариант на будущее, если сервер переведут на Compose v2 |
| `.env` | настройки, секреты уже сгенерированы |
| `README-DEPLOY.md` | этот файл |

Собирать на сервере ничего не нужно: `build:` в конфигурации отсутствует,
используются готовые образы.

Основной файл написан под установленный на сервере **`docker-compose` версии
1.x**: формат `2.4` — только он поддерживает ожидание готовности базы через
`depends_on.condition` — и без ключа `pull_policy`, которого в 1.x не
существует. Файл проверен настоящим `docker-compose 1.29.2`.

## Шаг 1. Проверить окружение

```bash
docker-compose version      # ожидается 1.x — основной путь
```

Если на сервере появится Compose v2 (команда `docker compose` через пробел),
используйте `docker-compose.v2.yml` — там прописан `pull_policy: never`.

Проверить занятые порты — **до** запуска:

```bash
docker ps --format '{{.Names}}: {{.Ports}}'
ss -tlnp
```

Проект по умолчанию занимает **8020**. Уже заняты соседями: **8090** —
`drop-detector`, **8081** — `fm-monitor`. Если 8020 тоже занят, поправьте
`WEB_PORT` в `.env` — менять сам `docker-compose.yml` не требуется.

```bash

```

## Шаг 4. Проверить настройки

### Вход в систему отключён

`AUTH_ENABLED=false` — по просьбе заказчика вход не запрашивается. Система
открыта всем, кто дотянулся до её порта, и все запросы выполняются от имени
служебного администратора. **Это допустимо только в закрытом контуре**: если
порт 8020 когда-нибудь окажется доступен извне, реестр окажется доступен вместе
с ним. Закройте порт на межсетевом экране для всего, кроме рабочих мест
аналитиков.

Код авторизации никуда не делся. Чтобы включить вход, поставьте в `.env`:

```
AUTH_ENABLED=true
```

и перезапустите: `docker-compose -p reestr-bs up -d`. Учётная запись
администратора создаётся при первом запуске независимо от этого параметра.
Логин — `admin`, пароль **сгенерирован при сборке этого комплекта** и записан
в `.env` рядом, строкой `FIRST_SUPERUSER_PASSWORD`. Постоянного пароля
в репозитории нет намеренно.

Смените его после первого входа: кнопка «Сменить пароль» в шапке либо раздел
«Пользователи». Смена живёт в базе, в томе — пересборки комплекта и обновления
образа её не трогают.

Если `FIRST_SUPERUSER_PASSWORD` оставить пустым, приложение выдаст случайный
пароль и покажет его в журнале **ровно один раз** — при создании учётной
записи, в рамке из знаков равенства:

```
docker-compose -p reestr-bs logs app | grep -A 2 "Создан администратор"
```

Не записали — остаётся только аварийный сброс, см. ниже.

### Если система уже разворачивалась на этом сервере

`FIRST_SUPERUSER_PASSWORD` применяется **только при создании** учётной записи.
Том с базой переживает обновление образа, поэтому при повторной установке
запись `admin` остаётся со старым паролем — тем, что действовал на момент
первой установки. **Пароль из нового комплекта не подействует.**

Если войти нечем, раскомментируйте в `.env` строку:

```
ADMIN_PASSWORD_RESET=true
```

После запуска войдите под паролем из `.env` этого комплекта, затем
**закомментируйте строку обратно** и повторите `docker-compose -p reestr-bs up -d`.
Пока параметр включён, пароль сбрасывается при каждом старте — приложение
предупреждает об этом в журнале.

Данные при сбросе не теряются: SQL алгоритмов, история правок, сохранённые
настройки и остальные учётные записи остаются на месте.

### Пароль ClickHouse задать обязательно

Система ходит в ClickHouse под учётной записью **`ai_doa`**, и её пароль
намеренно не хранится в репозитории — в `.env` комплекта поле пустое.
Впишите его перед первым запуском:

```
CLICKHOUSE_USER=ai_doa
CLICKHOUSE_PASSWORD=<пароль ai_doa>
```

Либо задайте позже через раздел «Настройки» в интерфейсе. Без пароля
подключения не будет, и в `/api/health` ClickHouse окажется недоступен.

Проверьте ещё одно значение, если оно отличается от типового:
* `OLLAMA_MODEL` — имя модели должно совпадать с зарегистрированным в Ollama
  буква в букву:

```bash
curl http://192.168.97.9:11434/api/tags
```

## Шаг 6. Убедиться, что работает

```bash
docker-compose -p reestr-bs logs app | grep -E 'алгоритмов|ClickHouse|Qwen|Интерфейс'
curl -s http://localhost:8020/api/health
```

В журнале при первом запуске должно быть:

```
Интерфейс раздаётся из /app/frontend/dist
ИИ Qwen:    http://192.168.97.9:11434 (doai-vision2:latest)
Режим чтения: планировщик пересчёта не запускается, таблицы результатов ведёт организация
Схема PostgreSQL проверена/создана
Создан администратор по умолчанию: admin
В bs_algorithms добавлено алгоритмов: 24
ClickHouse доступен, версия ...
```

Каталог содержит 24 алгоритма, из них действующих 23: БС-14 заведён
отключённым — его таблицы результата нет в объединении AFM_6_1_99.

### Откуда реестр берёт данные

Путей два, и приложение выбирает их само при первом обращении. Какой выбран —
видно в журнале.

**Основной: готовая сводная таблица.** `AFM_6_TEST.AFM_6_1_99_merged` собирается
скриптом организации, там же данные приводятся в порядок — убираются невидимые
символы и заглушки вместо ИИН, вычищается служебный текст из ФИО, схлопываются
повторы, подставляются наименования компаний, юрлицо-бенефициар разворачивается
до конечного физлица. Система берёт поля как есть и ничего не пересчитывает.
Строка в журнале:

```
Сводная таблица AFM_6_TEST.AFM_6_1_99_merged взята основой реестра
```

Считаются только баллы ball1/ball2/ball3, которых в сводной нет, и тип
собственности из `AFM_2_1_8` — без него не работает правило ТЗ о
государственных компаниях.

**Запасной: таблицы отдельных алгоритмов.** Включается, если сводной нет или
в ней не хватает полей. Это рабочий режим, а **не поломка** — так система
работала до появления сводной. В журнале будет одна из строк:

```
Сводной таблицы AFM_6_TEST.AFM_6_1_99_merged нет
Сводная таблица … не подходит, не хватает полей: …
Не удалось прочитать состав сводной таблицы …
```

Первая означает, что таблицы нет или она не видна учётной записи `ai_doa`.
Вторая называет недостающие поля. Третья — ошибку доступа к ClickHouse.

Имя задаётся переменной `MERGED_TABLE`; можно перечислить несколько через
запятую, берётся первое подходящее, пустое значение отключает основной путь
совсем. Подставлять `AFM_6_1_99` или `AFM_6_1_99_OLD` вместо `_merged` нельзя:
это промежуточные таблицы, они сводятся в неё, и чтение их дало бы часть данных.

На запасном пути строки ФИО, с которыми не справились правила разбора,
дочищаются моделью пачками по 25 и запоминаются в PostgreSQL — обращение к
модели идёт один раз на каждую новую строку. Отключается переменной
`AI_NAME_CLEANUP=false`. **Недоступность модели реестр не ломает**: такие имена
показываются по правилам, в журнале остаётся «Разбор имён моделью не удался».
Состав реестра, баллы и ключ сведения от этого не зависят — их считает SQL.

**При обновлении уже развёрнутой системы** числа будут другими: 10 новых
алгоритмов добавятся, прежние обновятся, и в журнале появится «Обновлено
алгоритмов из каталога». Если чей-то SQL правили через интерфейс, приложение
его не тронет и перечислит такие коды предупреждением «Не обновлены — SQL
правили через интерфейс». Эти алгоритмы останутся в старой редакции: сверьте
их вручную в разделе «Алгоритмы».

Строки «создано другим процессом» — норма: приложение работает в четыре
процесса, и они стартуют одновременно.

Открыть порт, если включён firewall:

```bash
firewall-cmd --add-port=8020/tcp --permanent && firewall-cmd --reload
# либо
ufw allow 8020/tcp
```

Интерфейс: **http://10.10.31.35:8020**, документация API — `/api/docs`
(работает без интернета, Swagger лежит внутри образа).

### Портрет бенефициара: витрины

В карточке лица собирается справка из шестнадцати витрин — финмониторинг,
пенсионные взносы, зарплата, госслужба, активы, адрес, учёты, должники,
инвалидность, ЕРДР. Шестнадцать запросов идут одновременно и независимо:
недоступность одной витрины не оставляет аналитика без справки.

Имена витрин заданы переменными `PORTRAIT_*` (см. `backend/app/core/config.py`).
Часть витрин лежит в базе по умолчанию, часть — в `pfr_dashboard`, и на разных
стендах это различается. Поэтому имя проверяется по системному словарю: не найдя
таблицу, служба пробует то же имя в соседней базе, а не найдя и там — пропускает
блок. В журнале это видно строкой:

```
Витрина <имя> не найдена — блок портрета пропущен
```

**Это не поломка.** Портрет собирается из того, что доступно, а пропуск помечен
в самом ответе — пустой блок не выдаётся за «сведений нет». Если нужная витрина
лежит под другим именем, поправьте соответствующую переменную `PORTRAIT_*`
в `.env` и перезапустите приложение.

Записи в витрины система не делает: доступ только на чтение.

## Шаг 7. Первая проверка реестра

Система подключена к ClickHouse **только на чтение**. Таблицы результатов
алгоритмов (`AFM_6_1_7` … `AFM_6_1_30`) ведёт организация, приложение их
не создаёт и не перезаписывает — оно читает готовые и собирает из них реестр.

Поэтому запускать алгоритмы не нужно и нельзя: кнопки запуска и полного
пересчёта в интерфейсе скрыты, а через API запрос будет отклонён. Ночное
расписание по той же причине не стартует — в журнале это видно строкой
«Режим чтения: планировщик пересчёта не запускается».

SQL алгоритмов остаётся в разделе **Алгоритмы** как описание критериев
отбора: по нему видно, на каком основании человек признан бенефициаром.

Что проверить после установки:

1. **Дашборд** — счётчики компаний и бенефициаров заполнены. Нули означают,
   что таблицы результатов пусты либо недоступны учётной записи `ai_doa`.
2. **Список ЮЛ** и **Список бенефициаров** — записи открываются, ИИН
   выглядят как двенадцать цифр, наименования читаемые. Мусор из источника
   (заглушки вместо ИИН, служебные строки вместо названия) разбирается на
   чтении, при сборке реестра.
3. **Структуры владения** — граф строится хотя бы для одной компании.
4. **Отчёты** — сформировать любой в xlsx и в pdf, проверить кириллицу.

Если счётчики пустые, смотрите доступность таблиц под `ai_doa`:

```bash
docker-compose -p reestr-bs exec app python -c "import urllib.request,urllib.parse; q=urllib.parse.quote('SHOW TABLES FROM AFM_6_TEST'); print(urllib.request.urlopen('http://192.168.122.45:8123/?query='+q, timeout=15).read().decode())"
```

### Если понадобится расчёт силами системы

Тогда учётной записи нужны права на создание таблиц в `AFM_6_TEST`, а в
`.env` — `CLICKHOUSE_READONLY=false`. Только после этого в интерфейсе
появятся запуск алгоритмов, полный пересчёт и ночное расписание. Порядок
запуска задан зависимостями: сначала самостоятельные алгоритмы, затем
БС-11, БС-13, БС-17, последним — замыкающий БС-24, который читает
результаты всех остальных. БС-13 идёт по электронным счетам-фактурам
(около 485 млн строк) и выполняется часами.

## Обновление версии

```bash
cd ~/reestr-bs
tar -xf /tmp/reestr-bs-deploy.tar
docker load -i images.tar.gz
docker-compose -p reestr-bs up -d --force-recreate
```

Тома сохраняются: настройки, SQL алгоритмов, история правок и учётные записи
остаются на месте.

Распаковка перезаписывает `.env` из комплекта. Если вы меняли в нём адреса,
пароль ClickHouse или порт — сохраните файл заранее:

```bash
cp .env .env.сохранённый
tar -xf /tmp/reestr-bs-deploy.tar
cp .env.сохранённый .env
```

Пароль администратора при обновлении не меняется: он живёт в базе, а не в `.env`.
Если войти нечем — см. `ADMIN_PASSWORD_RESET` в шаге 4.

## Эксплуатация

```bash
cd ~/reestr-bs
docker-compose -p reestr-bs ps
docker-compose -p reestr-bs logs -f app
docker-compose -p reestr-bs restart app
docker-compose -p reestr-bs down          # остановить, данные сохраняются
```

**`down -v` использовать нельзя** — флаг удалит тома вместе с SQL алгоритмов,
сохранёнными настройками и учётными записями.

Резервная копия метаданных:

```bash
docker-compose -p reestr-bs exec postgres pg_dump -U bs_registry bs_registry > ~/bs_registry_$(date +%F).sql
```

Данные проекта в томах с префиксом проекта — `reestr-bs_postgres-data`,
`reestr-bs_app-data`, `reestr-bs_app-logs`. С томами соседних проектов
не пересекаются.

## Если что-то пошло не так

**`docker-compose` ругается на неизвестный ключ.** Убедитесь, что запускаете
`docker-compose.yml`, а не `docker-compose.v2.yml`: во втором есть
`pull_policy`, которого версия 1.x не понимает.

**Compose пытается скачать образ и падает.** Образы не загружены: выполните
`docker load -i images.tar.gz` и проверьте `docker images`.

**Порт занят.** Поменяйте `WEB_PORT` в `.env` и повторите `up -d`.
Проверить, кто занял: `ss -tlnp | grep 8020`.

**Сеть или том с таким именем уже существует.** Значит, проект уже
разворачивался ранее. Посмотрите `docker network ls` и `docker volume ls`;
если это остатки прошлой установки — удалите их и повторите запуск.

**`status: degraded` в `/api/health`.** Приложение работает, но не видит
ClickHouse или Ollama. Проверьте с сервера:

```bash
curl http://192.168.122.45:8123/ping
curl http://192.168.97.9:11434/api/tags
```

**Поменяли адрес в `.env`, перезапустили — приложение ходит по-старому.**
Адрес был ранее сохранён через раздел «Настройки» в интерфейсе, а сохранённые
настройки **сильнее** переменных окружения. Посмотрите в самом разделе:
у каждого блока подписано, откуда взято значение. Полный сброс к переменным
окружения:

```bash
docker-compose -p reestr-bs exec app python -c "import pathlib; pathlib.Path('/app/data/settings.json').unlink(missing_ok=True)"
docker-compose -p reestr-bs restart app
```

**Модель отвечает не сразу, первый запрос будто зависает.** Ollama выгружает
модель из памяти при простое. В настройках задано `keep_alive=30m` — если
пауза дольше, первый запрос ждёт повторной загрузки модели на 122 млрд
параметров. Увеличьте значение в разделе «Настройки».

**Ответы модели выглядят обрезанными.** Проверьте «Размер контекста модели»
в разделе «Настройки»: при слишком малом значении Ollama молча отбрасывает
хвост промпта, без ошибки.
